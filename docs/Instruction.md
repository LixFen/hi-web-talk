# 项目落地实施计划

本文档基于 [Plan.md](Plan.md) 的总体设计，进一步把项目拆成可执行、可验收、可迭代的实施计划。目标不是重复概念，而是把“要做什么”“先做什么”“怎么判断做成了”写清楚，方便后续开发、答辩展示和阶段验收。

## 一、实施目标

本项目的落地目标可以概括为四层：

1. 先做出一个稳定可运行的本地 AI 对话工作台。
2. 再把“会话 = Block 图”的核心数据结构建立起来。
3. 再把多模型、分支对话、摘要、上下文构造逐步补齐。
4. 最后把聊天视图、链式视图、网状图视图统一到同一套数据模型上。

最终交付不是普通聊天页，而是一个单用户、本地运行、无数据库、基于 React + Node.js 的 AI 对话管理工具。

## 二、实施原则

### 1. 先骨架，后增强

开发顺序必须从最小闭环开始：

- 先能创建会话。
- 再能输入消息并获得回复。
- 再能把消息落盘。
- 再引入 Block 图和分支能力。
- 最后再做摘要、图视图和高级操作。

### 2. 数据结构优先于界面炫技

这个项目的核心不是界面，而是 Block 图和上下文算法。前端视觉可以保持克制，但底层数据结构必须先稳定。

### 3. 历史不可变

所有设计都要围绕“历史块不可随意篡改”展开。任何编辑、重生成、分支、复制挂接，原则上都只能产生新 Block，不能原地覆盖旧历史。

### 4. 模型归属写入块，不写入会话

会话不保存默认模型。每次发送时选择的模型必须写入当前新块，避免会话层和块层语义混乱。

### 5. 本地优先，文件持久化优先

项目默认不依赖数据库，所有状态以 JSON 文件为主。这样能保证：

- 结构简单。
- 便于调试。
- 便于展示。
- 便于后续迁移到别的存储层。

## 三、推荐开发顺序

### 阶段 0：项目骨架确认

目标是把运行环境、目录结构和开发入口固定下来。

要做的事：

- 确认前端 Vite 项目可启动。
- 确认 Node.js 服务端可启动。
- 确认前后端请求链路通畅。
- 确认本地配置文件目录存在。

验收标准：

- 页面可打开。
- 服务端可响应 `/api/chat`。
- 开发模式下前后端能联调。

### 阶段 1：最小聊天闭环

这一阶段只做最核心的“能聊”。

#### 前端

- 做一个基础聊天界面。
- 支持输入框输入。
- 支持发送按钮和回车发送。
- 支持消息列表展示。
- 支持空状态引导。
- 支持模型下拉选择。

#### 后端

- 提供最基础的聊天转发接口。
- 将 messages、provider、model 透传给对应模型接口。
- 返回统一格式的 reply。

#### 存储

- 先不做复杂图结构，只保存最基础的会话元数据和消息记录。

验收标准：

- 用户输入消息后能看到回复。
- 能切换模型并影响发送请求。
- 页面刷新后，基础会话数据可恢复。

### 阶段 2：Session 与 Block 基础模型

这一阶段开始进入项目核心。

#### 2.1 建立 Session

Session 需要成为一张对话图的入口对象，至少保存：

- sessionHash
- title
- createdAt
- updatedAt
- rootBlockSHA1
- activeBlockSHA1
- viewState.mode

落地要求：

- 新会话创建时自动生成 rootBlock。
- activeBlock 指向当前正在继续的链尾。
- 会话元数据与 block 数据分离保存。

#### 2.2 建立 Block

Block 是最小业务单元，至少包含：

- sha1
- blockType
- createdAt
- modelAlias
- prompt
- response
- tokenUsage
- contextLength
- parentBlockSHA1
- flags
- meta

落地要求：

- system block 作为根块。
- dialogue block 记录一次完整交互。
- 只存父引用，不存 children。
- SHA-1 规则固定，且不包含 parentBlockSHA1。

验收标准：

- 每次回复都能形成一个独立 block。
- 能从 session 读出当前活动链。
- 保存和读取不会破坏 SHA-1 稳定性。

### 阶段 3：当前链聊天视图

这一阶段把 Block 图压成普通聊天体验，让用户感觉依然像在聊天，但底层已经是图结构。

要做的事：

- 从 activeBlock 向上回溯 parentBlockSHA1。
- 构造线性 messages[] 给模型。
- 前端只展示当前活动链。
- 新消息总是追加到当前活动块后面。

验收标准：

- 用户感知上仍然是正常聊天。
- 实际数据已经转成 Block 链结构。
- 发送时能正确携带当前链上下文。

### 阶段 4：分支能力

这是项目最有辨识度的功能之一。

#### 4.1 任意块继续回复

支持从任意历史块继续聊天，而不是只能从最后一条消息往后追加。

#### 4.2 重新生成

重新生成不能覆盖旧结果，只能基于同一父块创建新的 sibling block。

#### 4.3 创建分支

用户选中某个历史块后，可以从该块向后开辟新链。

#### 4.4 删除规则

允许：

- 删除叶子块。
- 删除某块及其完整后继子树。

不允许：

- 删除中间块但保留后代。

验收标准：

- 分支创建后图结构稳定。
- 原历史块不被破坏。
- 图中任意节点都能被正确追溯。

### 阶段 5：上下文构造器 ContextBuilder

这是项目真正的算法核心。

#### 5.1 基础回溯

从当前块出发沿 parentBlockSHA1 回溯到 system root。

#### 5.2 过滤规则

支持：

- ignoreInContext 跳过。
- summaryPinned / preferSummary 走摘要替代。
- 根据上下文窗口限制裁剪历史。

#### 5.3 长度控制

同时支持：

- token 估算。
- 字符近似控制。

#### 5.4 system prompt 注入

最前面始终插入 system message，保证模型调用结构统一。

验收标准：

- 任意块都能正确构造出线性上下文。
- 上下文长度不会越界。
- 摘要替换逻辑可解释、可调试。

### 阶段 6：摘要系统

摘要系统是上下文压缩层，优先做成外置、独立、可失败记录的模块。

要做的事：

- 设计 summaries.json。
- 支持按 blockSHA1 查询摘要。
- 摘要失败时记录 status 和 errorMessage。
- 摘要生成采用懒加载。

验收标准：

- 摘要不会污染 block 本体。
- 摘要可独立生成、读取、更新。
- 失败有明确日志和状态。

### 阶段 7：错误日志系统

错误不写回正式对话块，而是进入独立错误日志。

要做的事：

- 记录会话、父块、prompt、模型、时间、错误信息。
- 提供错误回看入口。
- 支持调试用的原始错误信息保留。

验收标准：

- 模型调用失败时不丢失错误上下文。
- 错误记录与正式会话数据隔离。

### 阶段 8：模型管理

模型配置不绑会话，而是作为独立配置层。

要做的事：

- 支持模型增删改查。
- 支持 OpenAI 兼容接口。
- 支持 providerType、baseURL、apiKeyEncrypted、modelName 等字段。
- 支持是否启用、是否流式等配置。

验收标准：

- 多模型可以并存。
- 每次发送前能准确选择模型。
- 历史块保留各自的 modelAlias。

### 阶段 9：多视图前端

这个阶段把项目的图结构优势真正展示出来。

#### 9.1 聊天视图

- 只显示当前活动链。
- 体验接近普通聊天工具。

#### 9.2 当前卡片链视图

- 每个 block 显示为卡片。
- 支持复制、分支、查看 SHA1、标记 flags、查看 meta。

#### 9.3 网状图视图

- 展示整张会话图。
- 支持点击任意块并切换 active block。
- 支持直观看到分支关系。

验收标准：

- 同一份数据可在三种视图里一致展示。
- 视图切换不会破坏当前会话状态。

## 四、模块级落地拆分

### 前端模块

建议拆成以下功能模块：

- SessionListPage：会话列表页。
- ChatWorkspacePage：聊天工作区页。
- ChatView：当前链聊天视图。
- ChainCardView：链式卡片视图。
- GraphView：图视图。
- BlockCard：单个 Block 的展示组件。
- BlockMetaPanel：元数据面板。
- ErrorBlockCard：错误块展示组件。
- ModelSelector：当前发送模型选择器。
- ModelSettingsPanel：模型配置面板。
- SystemPromptPresetSelector：系统提示词预设选择器。
- PromptInputBox：输入框。

前端状态管理建议使用 Zustand，原因是：

- 状态类型清晰。
- 适合图结构和当前活动块状态。
- 比较适合本地单用户工具。

### 后端模块

建议拆成以下服务：

- SessionService：管理会话元数据。
- BlockGraphService：维护块关系。
- ContextBuilderService：构造发送上下文。
- ModelConfigService：管理模型配置。
- LLMProviderService：统一转发到不同模型提供方。
- SummaryService：生成和读取摘要。
- ErrorLogService：记录错误日志。

落地要求：

- 各服务职责单一。
- 图逻辑不混入 UI 逻辑。
- 上下文构造与模型请求解耦。

## 五、数据存储落地

推荐采用本地 JSON 文件结构：

- /data/sessions/{sessionHash}/session.json
- /data/sessions/{sessionHash}/summaries.json
- /data/sessions/{sessionHash}/errors.json
- /data/config/models.json
- /data/config/app-settings.json

实施重点：

1. 先做单会话文件读写闭环。
2. 再做多会话目录管理。
3. 再做摘要和错误日志的拆分文件。
4. 最后补全配置文件读写。

验收标准：

- 文件结构固定且清晰。
- 重启后状态可恢复。
- 不依赖数据库也能完整工作。

## 六、接口落地顺序

建议接口按照下面顺序实现：

### 1. Session API

- 创建会话。
- 读取会话。
- 删除会话。
- 切换 active block。

### 2. Block API

- reply。
- regenerate。
- branch。
- copy-subtree。
- delete subtree。
- patch flags。
- get meta。

### 3. Summary API

- 生成摘要。
- 查询摘要。
- 更新摘要状态。

### 4. Model API

- 列表读取。
- 新增。
- 更新。
- 删除。
- 启用/停用。

验收标准：

- API 命名语义清晰。
- 前端调用时不需要知道底层文件结构。
- 接口足够支撑后续多视图与图操作。

## 七、建议的里程碑

### 里程碑 A：可聊天

完成目标：

- 单会话。
- 单模型。
- 可发送、可回复、可保存。

### 里程碑 B：可分支

完成目标：

- Block 图结构。
- 任意块继续聊天。
- 重新生成产生 sibling。

### 里程碑 C：可压缩

完成目标：

- ContextBuilder。
- 摘要替代。
- 上下文长度控制。

### 里程碑 D：可展示

完成目标：

- 聊天视图。
- 链式卡片视图。
- 网状图视图。

### 里程碑 E：可交付

完成目标：

- 错误日志。
- 配置管理。
- 本地持久化。
- 移动端基本可用。

## 八、每阶段验收清单

### 功能验收

- 是否可以创建新会话。
- 是否可以选择模型。
- 是否可以发送消息。
- 是否可以形成 Block。
- 是否可以从历史块继续回复。
- 是否可以生成分支。
- 是否可以读取摘要。
- 是否可以记录错误。

### 数据验收

- session.json 是否可恢复会话。
- blocks 的 SHA-1 是否稳定。
- parentBlockSHA1 是否正确。
- summaries.json 是否独立。
- errors.json 是否独立。

### 交互验收

- 当前活动块是否高亮。
- 不同视图切换是否流畅。
- 模型切换是否在发送时生效。
- 小屏是否还能正常阅读和输入。

## 九、风险与处理策略

### 风险 1：图结构实现过早复杂化

处理策略：先保证单链可运行，再逐步引入分支和复制。

### 风险 2：上下文构造逻辑过重

处理策略：把 ContextBuilder 独立出来，先写纯函数版本，再接服务层。

### 风险 3：摘要系统侵入核心路径

处理策略：摘要必须外置、可选、失败可降级，不要阻塞主聊天流程。

### 风险 4：前端视图过多导致复杂度上升

处理策略：统一数据源，所有视图只读同一份 session/block 状态。

### 风险 5：JSON 文件持久化在并发写入时出问题

处理策略：单用户场景下可以通过串行写入和临时文件原子替换降低风险。

## 十、最终交付标准

当项目真正完成时，应该满足以下条件：

- 可以本地启动。
- 可以管理多个会话。
- 可以切换多模型。
- 可以在任意历史节点继续对话。
- 可以看到分支结构。
- 可以通过摘要压缩上下文。
- 可以通过网状图查看整张对话图。
- 所有核心数据都能通过 JSON 文件持久化。

## 十一、建议的下一步任务

如果现在就开始真正开发，建议按这个顺序推进：

1. 先完成 Session / Block 的文件结构定义。
2. 再实现 ContextBuilder 的纯函数版本。
3. 再补前端当前链聊天视图。
4. 再做分支和重新生成。
5. 再加摘要和错误日志。
6. 最后再做图视图与增强交互。

这条路线最稳，因为它把项目的核心差异化能力放在了最前面，同时又不会在一开始就被界面和细节拖慢。
